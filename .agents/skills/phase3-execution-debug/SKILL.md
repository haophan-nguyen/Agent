# Phase 3 - Execution & Debug

This skill covers Phase 3 of Requirement & Test Design; Development & Build; Execution & Debug; Verification & Report. The approved Test Design governs tests, acceptance criteria, prerequisites, and evidence. Derive project, target, operating system, interfaces, tools, and configurations from that design and retained project records; no particular application, MCU, SDK, or framework is assumed.

Creating, updating, or discovering this skill grants no execution authority. Do not modify application source, build configuration, firmware, or the approved Test Design; do not rebuild, commit, push, or automatically start another phase. Final verification requires engineer acceptance.

## Skill Maintenance vs Execution Boundary

Apply this boundary before selecting a mode. It takes precedence over the mode-selection, approval-reuse, and continuation instructions below.

1. **Documentation-only maintenance:** When the task is to create, review, or improve this skill, operate only in skill-maintenance mode. Inspect relevant documentation and validate the skill as needed; change only the skill files authorized by the engineer. Do not invoke the Phase 3 execute or audit/report-only workflow, perform execution preparation or host/hardware diagnostics, access hardware, or create/update execution reports or ledgers as part of maintenance.
2. **No execution in the same maintenance task:** Never start or resume Phase 3 within that task, even if the request also mentions resuming execution. Do not turn a mixed maintenance/execution request or an operational approval response into permission to execute during maintenance. Defer execution to a separate task.
3. **Complete, present, and stop:** Finish the authorized skill changes, present them for engineer review, and stop. A separate, explicit engineer request made after maintenance is complete is required to start or resume execution. That later task must satisfy the entry gate and obtain applicable current operation approvals; approval of skill changes alone is not execution authority.
4. **Invalid approvals cannot be reused:** Never reuse previously withdrawn, expired, or denied hardware approvals. Retain them only as historical records; any later operation requires a new explicit scoped grant. Reuse instructions elsewhere apply only to approvals that remain valid for the current scope.
5. **Engineer STOP:** Cancel all unstarted operations and preserve existing evidence, checkpoint state, and recovery counters. Report any operation already executed or still in progress, its actual result/status, and the last known target state; identify unknowns explicitly. Assess safety before interrupting an in-progress state-changing hardware command; do not forcibly interrupt it by default. Stop before any subsequent operation, including retries or restoration/reset commands; a STOP does not authorize further hardware activity.

## Select the mode

Use the engineer's requested mode. Infer it only when the request is unambiguous; otherwise continue safe read-only discovery and clarify before execution.

| Mode | Scope |
| --- | --- |
| `execute` | Validate the entry gate; prepare and execute approved tests; collect observations; classify and investigate failures; perform authorized recovery and bounded retesting; write the Phase 3 report. |
| `audit/report-only` | Inspect existing designs, approvals, execution logs, measurements, and debugging records using read-only methods; verify references/hashes; write a new versioned audit report. Do not rebuild, reflash, re-execute tests, launch the application, interact with live hardware, change application source, or alter existing evidence. |

An audit may assess historical Phase 3 authorization without having current execution authority. Missing historical authority is a finding, not permission to rerun work. If an audit request also asks for execution or repairs, record the conflict and seek clarification before those actions; independent audit work may continue. Change modes only with engineer authorization.

## Validate the entry gate

Before executing a test or interacting with a target:

1. Read applicable `AGENTS.md` instructions, the complete approved Test Design and its approval record, and the relevant Phase 2 report and available supporting evidence. Identify exact document IDs, versions, references, approved requirements, and test IDs. Do not silently choose between conflicting baselines.
2. Verify explicit engineer authorization to enter Phase 3 for this task and baseline. Phase 2 completion, a prior successful run, and availability of a binary do not grant it. Reuse verified authorization within its existing scope rather than asking again.
3. Establish source revision plus relevant dirty/untracked input identity, firmware path/size/SHA-256, build configuration, toolchain/SDK provenance, and their association with Phase 2 evidence. For host-only tests, identify the actual executable/package and mark target-image fields inapplicable with a reason. Do not rebuild to fill provenance gaps.
4. Identify the exact target/device, board revision and connections where relevant, current/loaded image identity, required setup, test sequence/dependencies, acceptance criteria, measurement requirements, and evidence needed per test. Distinguish an image selected for use from proof that the image is running on the identified target. Use approved programming/readback records or another design-accepted identity method; unknown identity blocks affected results.
5. Review unresolved Phase 2 issues, stale or missing evidence, and execution hazards. Verify explicit engineer acceptance of relevant residual risks and its scope; a waiver cannot establish a PASS or replace required evidence. Block tests whose prerequisites remain unmet.
6. Discover available host execution, programming, debug, serial, harness, and instrument tools through documentation, saved configuration, and non-invasive inspection. Record versions and access where verifiable. Inspect commands, wrappers, hooks, and launch configurations before running them: a test/debug command may also build, flash, reset, or change device state. Availability unverified does not mean equipment is absent.
7. Verify operation-specific hardware authority: target, exact image where applicable, operation, permitted scope, and restrictions. Engineer designation of an image and authorization to program it are separate facts. Check current execution permissions independently.

Record each gate item and its evidence; distinguish an unmet prerequisite from an approval checkpoint awaiting a response. A missing global gate, such as Phase 3 authorization or an approved design, stops all execution. A test-specific blocker stops that test and its dependents; independent approved tests may continue if their own gates are satisfied. Safe inspection and evidence checkpoints may continue. Follow the interactive checkpoint below before ending a path that needs a requestable engineer decision; never record approval on the engineer's behalf.

### Hard blockers and reviewable risks

- **Hard blockers:** Missing mandatory authorization, unsafe hardware state, unverified critical target identity, mandatory test evidence, or another non-waivable design/safety prerequisite. Obtain the missing authorization or establish the prerequisite; risk acceptance cannot waive it. State precisely which operation is prevented and what resolves it.
- **Reviewable risks:** Incomplete historical provenance, noncritical evidence gaps, or residual uncertainties that do not invalidate mandatory safety, identity, or test criteria. Present known evidence, uncertainty, impact, mitigations, and the exact bounded continuation proposed; request an explicit scoped engineer disposition. Do not silently treat every historical gap as a terminal blocker or accept the risk on the engineer's behalf.
- Determine criticality from the approved design and the proposed operation; do not relabel a mandatory prerequisite as a reviewable risk to proceed. Acceptance permits only its stated continuation and does not certify missing history, replace test evidence, or convert a result to PASS.
- A specifically authorized identity-establishment operation may resolve unknown loaded-image identity before tests. It still requires enough physical target identification and safe setup for that operation; its authorization does not waive the identity evidence required for later test results.

## Plan, prepare, and execute

In `execute`, follow **Prepare -> Execute -> Observe -> Evaluate -> Continue or Debug**.

1. Map approved test IDs to criteria, requirements, prerequisites, dependencies, exact commands/operations, environments, evidence, and applicable approvals. Record concise decision rationales. Define finite command timeouts and safe stop behavior consistent with the design; do not shorten required observation periods or alter repetitions to obtain a pass.
2. Establish a task-specific evidence directory and execution ledger using [references/report-format.md](references/report-format.md). Preserve the starting source/configuration state. Prepare approved fixtures, application launch, logging, serial capture, and instruments only within authorized scope. Record measurement connections, settings, units, and accuracy relevant to the criterion.
3. Assign an execution ID to each test attempt. Confirm the identified executable/image, target, configuration, permissions, and required evidence capture before starting it. Run approved host commands, launch approved applications, and use authorized debugging/measurement tools autonomously when available. Do not use a combined build/flash/test action when any included operation is outside scope.
4. For hardware, automated flashing, reset, debugger attachment/interaction, register access, instrument control, and other disruptive operations require suitable tools and specific engineer authorization. A nominally read-only debug/measurement operation may halt a core, clear registers, load a stub, or disturb timing; assess its actual effects. Engineer involvement can be an attributable scoped authorization plus review of recorded operations; honor any requirement for physical supervision. If task authority is missing, explicitly request it through the interactive checkpoint before closing the path. If suitable automation is unavailable, offer concrete engineer-assisted steps and required evidence within the proposed scope; wait for actual approval/results. Suggested steps are not completed actions.
5. Observe and retain actual outputs, exit codes, target state, serial/log data, registers, and measurements relevant to the test. Distinguish quantitative measurements, visual observations, source calculations, and inferences. Mark debug-instrumented runs and their effects; do not use altered timing as evidence for normal-operation criteria unless the design permits it.
6. Evaluate against unchanged approved criteria. Use PASS, FAIL, BLOCKED, or NOT RUN as defined in the report contract. Tool exit success alone cannot establish functional success. Missing capture is not firmware success; a visual observation cannot establish quantitative timing accuracy. Preserve demonstrated violations even when other evidence is unavailable.
7. Continue independent tests when safe. On failed or blocked execution, enter the loop below. Capture diagnostic evidence before destructive recovery where safely possible; if recovery would erase required evidence that cannot be retained, stop the affected operation and report it.

## Debug and recover within scope

Follow **Execute -> Observe -> Classify -> Diagnose -> Recover -> Retest**. Read [references/failure-playbook.md](references/failure-playbook.md) when classifying a failure or selecting diagnostics/recovery; it defines all eight categories and their authorization boundaries.

1. Open or link a failure ID; record symptom, test/execution ID, raw evidence, and test status separately from failure category. Classify provisionally and revise when evidence supports it; preserve the classification history. Use UNKNOWN rather than inventing a cause.
2. Form a concise root-cause hypothesis supported by evidence. Choose the next diagnostic or recovery action, its expected observable result, and the technical reason it can distinguish or address the suspected cause. Record conclusions and short rationales, not hidden chain-of-thought.
3. Check the action against the approved design, mode, target/image scope, current permissions, preservation requirements, and remaining retry budget. A playbook recommendation is not authorization. Read-only source inspection is allowed; modifying source/build inputs requires a separately authorized return to Phase 2. Requirement/design changes require a separately authorized return to Phase 1. Hardware intervention or extra permissions requires engineer action.
4. Perform only authorized actions. Obtain missing engineer task authority through the interactive checkpoint first. For a command requiring permission escalation, use the execution environment's approval mechanism for the concrete operation before running it outside current permissions. Engineer Phase 3 approval does not waive that boundary, and native tool approval does not supply missing hardware/task authority. Do not submit a hardware command to a native prompt while its engineer approval is pending. On denial/unavailability, stop that operation, consider independently authorized alternatives, and record PERMISSION/BLOCKED where no valid path remains; do not bypass the boundary.
5. Retest with the same approved criteria, required repetitions, image/configuration identity, and evidence standard. Link the new execution ID to the original failure and recovery attempt. A completed corrective action is not successful recovery without adequate retest evidence; keep original failures and intermittent behavior visible.
6. Record the result, residual risk, issue disposition, and continue/retry/escalate decision. If baseline changes are approved in another phase, stop this Phase 3 run; later execution needs updated build evidence, identity, and applicable entry authority. Do not perform the earlier phase under this skill.

### Recovery budget and stopping rules

- Default to at most **3 recovery attempts per issue**, using a stricter approved limit when specified. Any increase requires explicit engineer authorization with a new finite limit; do not infer it from an instruction to keep investigating.
- One recovery attempt consists of one state-restoring intervention and its associated validating retest, or a retest-only retry when no intervention is used. Count it when the intervention (or retest-only retry) is issued, including a failed or uncertain outcome. Its validating retest does not consume a second attempt and may complete the final allowed attempt if safe and authorized; it grants no further recovery action. Record scope before acting; distinct interventions count separately, so do not hide multiple resets/reflashes in one attempt. Initial execution and passive diagnostics do not consume attempts. Approved planned repetitions remain tests, not extra recovery allowance.
- Maintain the issue's count across reclassification, related test failures, and resumed sessions. Link shared-cause issues; renaming an issue or restarting a conversation does not renew the budget. Recover the prior ledger before continuing; if its count cannot be established, block further recovery until clarified.
- Do not repeat an unchanged action without new evidence or a recorded, justified reason. Bound diagnostics by useful progress and agreed operation timeouts; do not substitute endless diagnosis for the recovery cap.
- Stop earlier when evidence/identity becomes unreliable, no meaningful progress is possible, required safety/setup conditions fail, the next action exceeds scope/permission, or continuation could damage hardware or destroy required evidence. At budget exhaustion, start no new recovery attempt; complete only the final attempt's safe, authorized validation, then escalate unresolved issues with evidence and a concrete next decision.
- These are skill-level operating rules, not guaranteed runtime enforcement. Disclose when stronger enforcement requires an external runner, counters persisted outside the model, access controls, or hardware interlocks; the skill does not supply them.

## Approval checkpoints

Maintain attributable approvals for Phase 3 entry; firmware designation and flashing; disruptive hardware/debug/instrument actions; permission escalation; changes outside scope; return to Phase 1/2; and disposition of relevant risks or unresolved blockers. Continue autonomously within existing approvals. Group related operations into one clearly bounded request when their prerequisites and effects can be reviewed safely; keep risk acceptance and operation authorization separately answerable. Do not request the same granted scope repeatedly.

When a required operation or reviewable risk needs an engineer decision:

1. Prepare a concrete checkpoint with an ID, affected test/failure IDs, exact command/operation and working directory, target/probe, firmware path/configuration/hash, side effects, risks, prerequisites, permitted scope, finite operation/retry limits, and exclusions. Explain what an approval would permit and what would remain blocked. If a critical detail is unknown, request it rather than asking for unbounded authority.
2. **Present an explicit approval request in the conversation before ending the workflow.** Clearly ask the engineer to **APPROVE, DENY, or DEFER** the stated scope. A proposed command in a report or a ledger entry alone is not an approval request. Use the available conversation input mechanism or a direct conversational request; do not silently produce a terminal BLOCKED report instead.
3. Save the checkpoint and execution context in the evidence ledger: completed/pending actions, evidence references, baseline/target identity, existing grants and limits, failure IDs and recovery counts, request/response state, and exact next action. Keep checkpoint state such as `AWAITING_RESPONSE` separate from test status. Requests, waiting, and responses consume no recovery attempts.
4. Wait for an explicit response before the restricted operation. Continue only independent already-authorized work meanwhile. If the turn must end while waiting, present the pending request and resume point, preserving the workflow as awaiting engineer response. **Never interpret silence, elapsed time, or a generic instruction to continue as approval of an unstated scope.**
5. **APPROVE:** Record the attributable response, exact scope/conditions and reference. Resolve all remaining hard prerequisites and any separate native permission before acting; then continue within the grant without asking again. Partial/ambiguous approval covers only clearly granted scope; clarify material ambiguity.
6. **DENY:** Record the decision; do not repeatedly ask or bypass it. Seek an independently authorized alternative with acceptable effects and evidence. If none remains, record the affected work as BLOCKED and finalize the path with its reason.
7. **DEFER:** Record the pending checkpoint and any engineer conditions, preserve state and counters, and pause dependent work. Defer is not denial, approval, or completed execution. Resume from this checkpoint when the engineer decides; do not repeat completed discovery/diagnostics unless evidence shows relevant state changed. Do not issue a terminal report solely for the pending decision unless the engineer explicitly asks to close the run.

Preserve the request, actual response (or no response), native permission outcome, and subsequent actions as separate attributable events using the report contract. Engineer task approval and native tool/sandbox permission approval are distinct; request only the missing layer. Risk acceptance never substitutes for mandatory authorization, safe setup, critical identity, or required passing evidence.

## Audit, report, and stop

In `audit/report-only`, compare existing execution/recovery records with the complete approved design, entry gates, permissions, retry limits, evidence rules, and exit criteria. Attribute historical actions and distinguish prior claims from inspected raw evidence. Hash matches establish identity, not proof of execution or authorization. Record gaps and scope violations without repairing them or reconstructing missing history. Apply the failure playbook when interpreting recorded failures; perform no live diagnosis or recovery.

Read [references/report-format.md](references/report-format.md) for evidence checkpoints and final reporting. In execute mode, create the final versioned report under `docs/reports/` after the authorized execution path completes, is denied with no independently authorized continuation, or cannot continue because of a genuine unresolved hard blocker. Request an available engineer decision first; an unasked or unanswered approval is not sufficient reason to terminate with a BLOCKED report. While waiting or deferred, maintain nonterminal evidence checkpoints. In audit mode, finish the requested read-only assessment and report historical approval gaps without initiating restricted execution. Use all nine required sections for final reports, ISO 8601 timestamps with numeric UTC offsets, and actual recorded precision. Do not include geographical timezone identifiers or invent timestamps, approvals, logs, measurements, or explanations. Reference retained raw evidence without rewriting it.

Before finishing, summarize completed tests and counts of PASS, FAIL, BLOCKED, and NOT RUN; verify available evidence references and identity associations; list unresolved issues/classifications, recovery history, remaining risks, and required engineer actions. Report Phase 3 as complete for engineer review, partially complete, or blocked, with the basis. A complete audit does not establish complete historical execution. Prepare Phase 4 handoff information and stop for engineer review; do not begin Phase 4 or claim final acceptance without explicit engineer evidence.

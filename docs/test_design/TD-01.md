The baseline source predicts 12,000,000 ticks / 12,000,000 Hz = 1000 ms per toggle, or 1000 ms ON + 1000 ms OFF = 2000 ms per complete cycle. This is a source-based calculation, not a hardware measurement.

The generated peripheral settings also describe a 10 ms interval, inconsistent with the executable configuration. Neither that comment nor the 48 MHz definition should be treated as the actual timing source.

## Requirements and acceptance criteria

| ID | Requirement | Approved acceptance criterion |
| --- | --- | --- |
| R1 | LED remains ON for a nominal 500 ms. | Every measured complete ON interval is 475–525 ms. |
| R2 | LED remains OFF for a nominal 500 ms. | Every measured complete OFF interval is 475–525 ms. |
| R3 | One complete blink cycle takes approximately 1000 ms. | Every measured cycle is 950–1050 ms; duty cycle is 47.5–52.5%. |
| R4 | Existing board initialization and GPIO functionality remain unchanged. | Preserve initialization calls and order, the 12 MHz clock selection, pin routing/electrical configuration, output direction, initial ON state, LED mapping, and existing GPIO toggle operation. |
| R5 | Preserve existing SysTick interrupt priority and configuration as appropriate. | The timing change preserves interrupt priority and the `CTRL.CLKSOURCE`, `CTRL.TICKINT`, and `CTRL.ENABLE` configuration bits. Only the reload interval and current counter phase intentionally change. Verify this during development and subsequently on target. |

The engineer explicitly approved the ±5% timing tolerance in TD-01 v1.1. This tolerance originated in the test design rather than the original requirement; it is now part of the approved acceptance criteria.

## Assumptions and implementation constraints

1. The target remains FRDM-MCXN236 with the existing 12 MHz FRO core-clock configuration.
2. Hardware timing acceptance covers complete intervals after application timing configuration. Time from reset to the first transition includes startup work; an exact 500 ms interval from reset is not required. Preserve the existing initial ON state.
3. The approved production-source change is limited to `main()` in `frdmmcxn236_led_blinky/led_blinky.c`, immediately after the existing `BOARD_InitHardware()` call. Configure a 500 ms SysTick interval using `SystemCoreClock` and reset the current count. A new include or timing constant, if needed, belongs in this same file. Implementation remains deferred until the separate Phase 2 instruction.
4. At 12 MHz, the interval requires 6,000,000 ticks, so `LOAD` must be 5,999,999. This is within the 24-bit SysTick reload range. Validate the computed reload before use.
5. Leave `SysTick_Handler()` and its GPIO toggle call unchanged. Leave board initialization, generated peripheral files, clock and pin files, LED definitions, build configuration, and SDK sources unchanged.
6. Preserve the SysTick priority present after `BOARD_InitHardware()` returns; do not assume a numerical priority. Inspect any proposed helper API for side effects. In the inspected local CMSIS implementation, `SysTick_Config()` also sets the interrupt priority, so it must not be used in a way that changes the existing priority.
7. Preserve the existing SysTick processor-clock selection, interrupt enablement, and enabled state after the update. If temporary masking or timer disabling is necessary, restore the prior interrupt-mask and timer-control configuration. Do not introduce persistent changes to unrelated interrupt configuration.
8. Compare configuration bits rather than transient status. `COUNTFLAG`, the live counter value, and the intentionally changed reload are not required to remain identical.
9. Firmware measurement must run without debugger halts, single-stepping, or ISR instrumentation that distorts timing. Perform register inspection separately from timing capture.

## Risks, limitations, and unresolved items

- FRO accuracy, interrupt latency, and instrument accuracy affect measured timing. Visual observation alone cannot establish millisecond timing accuracy.
- Debugger halts can distort the first interval and waveform timing. Keep T09 register inspection separate from uninterrupted timing tests.
- Generated peripheral metadata disagrees with the current executable configuration. This design leaves those files unchanged; future regeneration may change behavior and requires review.
- A different core-clock configuration may exceed the SysTick reload range or change timing. Such a change is outside this design and requires review.
- SDK and compiler paths exist, but configuration/build readiness has not been tested. No build success is claimed.
- Board access, instrument availability, probe connection, designated hardware-test image, and execution evidence remain unresolved until engineer-supported execution.
- Engineer approval of version 1.1 is complete. Phase 2 remains deferred until the engineer provides a separate instruction to begin development.
